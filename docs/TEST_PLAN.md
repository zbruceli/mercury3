# Test plan

This project has two kinds of testing:

- **A. Software tests** check that the harness is correct.
- **B. Experiment protocol** checks that the measurements are valid.

Both are required before any number goes into the blog.

---

## A. Software tests (harness correctness)

### A1. Unit tests (`tests/unit`, offline, run on every change)
| Area | What is tested | Feature |
|---|---|---|
| Schemas | `ChatRequest`/`ChatResult` validation; config YAML validation rejects unknown keys | F1.1, F3.1 |
| Adapters | Request mapping per provider (e.g. Mercury `reasoning_effort`/`diffusing` placed correctly; Anthropic tool format) using recorded fixtures | F1.2–F1.5 |
| Stream parsing | SSE fixtures for normal streaming, **diffusing streams (full-text frames)**, the usage-only final chunk, `[DONE]`, malformed lines | F2.1, F2.2, F2.6 |
| Timing | Injected fake clock produces correct TTFT/decode/total; first *non-empty* content defines TTFT | F2.1 |
| Retry/backoff | 429/503 retried with backoff; 400/401/404 not retried; retries flagged in the log | F1.6 |
| Rate limiter | Token-bucket behaviour under burst | F1.7 |
| Cost engine | Cached tokens billed at the cached rate; reasoning tokens not double-counted (they're inside `completion_tokens`) | F6.3 |
| Code extraction | Fenced, unfenced, multiple blocks, trailing prose | F4.2 |
| pass@k | Matches the reference unbiased estimator on known vectors | F4.4 |
| SQL scorer | Order-insensitive set comparison, NULL handling, float tolerance, ORDER BY sensitivity | F5.4 |
| Tool validity | Valid, invalid-JSON, and schema-violating argument cases | F5.5 |
| SQL sandbox | Write statements rejected (read-only connection); timeout enforced | F5.2 |
| Stats | Bootstrap CI deterministic given an RNG seed | F6.2 |

Coverage target: ≥85% on `providers/`, `timing`, `metrics`, `cost`, and `scoring`.

### A2. Contract tests (`tests/contract`, offline)
- Recorded real responses (one per provider × {plain, streamed, tool call, structured output, diffusing}) are replayed through the full pipeline. Recordings live in `tests/fixtures/recordings/` with secrets removed.
- These detect SDK or response-shape drift when re-recorded.

### A3. Live smoke tests (`tests/live`, marker `@pytest.mark.live`, manual or pre-run only)
- Each configured model: one short completion, one stream, one tool call, and one strict JSON-schema output. Mercury additionally runs one `diffusing` stream and each `reasoning_effort` value.
- Assert: 2xx, usage present, no unexpected `warning`, and the server-returned model ID matches the config.
- Budget: < 50k tokens total. Never run in CI.

### A4. Pipeline (end-to-end dry) tests
- `dllm-eval run --dry-run` on each experiment config produces the expected job count and cost estimate.
- A mini run (3 items × 1 model, fake provider) → analyze → charts render without error.

## B. Experiment protocol (measurement validity)

### B1. Pre-flight checklist (before every real run)
- [ ] `dllm-eval smoke` passes for all models in the config
- [ ] Model IDs and prices in `configs/models.yaml` were re-verified within 7 days (`verified_on` field)
- [ ] Network baseline captured; same host/region as previous runs
- [ ] Dry-run cost is within budget; budget guard is set
- [ ] Git working tree clean (SHA recorded in the manifest)

### B2. Pilot runs
- 10 items × all models × 3 repeats for each use case.
- Use the pilot to measure the variance and size n so that the CI targets in the PRD are met.
- Manually inspect 10 outputs per model for prompt/extraction problems before scaling up.

### B3. Validity controls
| Threat | Control |
|---|---|
| Network/time-of-day noise | Randomised interleaving; ≥3 time windows; network baseline subtracted in a sensitivity analysis |
| No seed / sampling variance | n ≥ 5 quality samples; CIs on everything |
| Temperature mismatch | All models at 0.5 where allowed; log `warning`; sensitivity arm at provider defaults |
| Reasoning-token confound | Report visible vs. reasoning tokens; compare at matched effort tiers |
| Prompt bias toward one model | Single neutral prompt, written before the pilot and frozen; no per-model tuning in the primary arm |
| Benchmark contamination | LiveCodeBench post-cutoff subset reported separately |
| Extraction failures misread as model failures | Track extraction-failure rate separately; manual audit of a sample |
| Architecture vs. hardware | Fast-hardware AR control (PRD R13) |
| Cold start / caching | Discard the first call per model per run window; report cache hits |
| Retries skewing latency | Retried calls excluded from latency stats, counted separately |

### B4. Acceptance criteria for publishing a number
1. It comes from a run whose manifest passes B1.
2. CI half-widths meet the PRD targets (≤3 pp pass@1/EX; ≤10% p50 latency).
3. It can be regenerated by `dllm-eval analyze <run_id>` with no API calls.
4. It carries an "as of" footnote: model ID, date, tier, and region.
5. A second person (or a fresh Claude session) can reproduce the chart from the run directory.
